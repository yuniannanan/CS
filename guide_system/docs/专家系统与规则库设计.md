# 专家系统与规则库设计文档

## 1. 概述

智能导医系统的推理核心采用 **符号主义规则推理 + 加权置信度计算** 的混合架构。系统通过预定义的 IF-THEN 规则将患者症状映射到推荐科室，并支持组合症状推理、严重度升级和多规则共识机制。

## 2. 架构设计

### 2.1 推理流程

```
用户输入(自然语言)
    │
    ▼
┌─────────────────┐
│ SymptomExtractor │  ← 分词 + 精确匹配 + 同义词匹配 + 模糊匹配
│  症状提取引擎      │
└────────┬────────┘
         │ [症状列表 + 置信度]
         ▼
┌─────────────────┐
│  ExpertSystem    │  ← IF-THEN规则匹配 + 组合推理 + 严重度升级
│  专家系统推理机    │
└────────┬────────┘
         │ [推荐科室 + 置信度 + 分诊依据]
         ▼
┌─────────────────┐
│  ResultDisplay   │  ← 展示推荐结果 + 备选科室 + 就诊导航
│  结果展示模块      │
└─────────────────┘
```

### 2.2 规则匹配策略

| 匹配类型 | 触发条件 | 置信度计算 | 权重 |
|---------|---------|-----------|------|
| **单症状规则** | 症状ID精确匹配 | `症状置信度 × 规则权重 × 严重度系数` | 标准 |
| **组合规则** | 所有必需症状ID均命中 | `平均置信度 × 规则权重 × 严重度系数 × 1.2` | +20% 加权 |
| **排除规则** | 触发症状命中 | 从候选科室中移除此科室 | — |

## 3. 规则库设计

### 3.1 数据模型

```sql
CREATE TABLE rules (
    rule_id       INTEGER PRIMARY KEY,
    symptom_id    INTEGER,         -- 主触发症状ID
    dept_id       INTEGER,         -- 推荐科室ID
    rule_weight   FLOAT DEFAULT 1.0,  -- 规则权重 (0.1~2.0)
    conditions    VARCHAR(500),    -- IF-THEN条件描述
    severity      VARCHAR(20),     -- 严重度: low/medium/high/critical
    rule_type     VARCHAR(20),     -- 规则类型: single/compound/exclusion
    extra_symptom_ids TEXT,         -- 附加症状ID列表(JSON)
    conditions_detail TEXT,         -- 详细条件说明
    is_active     INTEGER DEFAULT 1 -- 是否启用
);
```

### 3.2 严重度等级

| 等级 | 系数 | 适用场景 |
|------|------|---------|
| **critical** | 1.5 | 危及生命：急性心梗、脑膜炎、严重过敏 |
| **high** | 1.3 | 需紧急诊治：持续性胸痛、不明原因体重下降 |
| **medium** | 1.0 | 常规就诊：咳嗽、腹痛、关节疼痛 |
| **low** | 0.8 | 轻微症状：咽部不适、食欲减退 |

### 3.3 规则类型

| 类型 | 说明 | 示例 |
|------|------|------|
| **single** | 单症状→单科室 | IF 咳嗽 THEN 呼吸内科 |
| **compound** | 多症状 AND 逻辑 → 科室 | IF 发热+咳嗽 THEN 呼吸内科（上感） |
| **exclusion** | 排除特定科室 | IF 单纯咳嗽 THEN 排除急诊科 |

## 5. 核心算法

### 5.1 置信度计算

```
单规则置信度 = symptom_confidence × rule_weight × severity_multiplier

多规则综合 = Σ(rule_confidence) / rule_count
            × combo_bonus(1.0 + 0.08 × (rule_count - 1))
            × dilution(1.0 / (1.0 + 0.05 × (total_symptoms - 1)))
            → clamp(0.0, 1.0)
```

### 5.2 严重度升级

当任意 **critical** 或 **high** 级别规则命中时：
- 结果标注 severity 标签
- 匹配科室的分数额外 ×1.2
- 前端以颜色高亮显示（红色=危急，橙色=高危）

### 5.3 排除机制

排除规则在最后阶段执行——所有候选科室计算完成后，从结果集中移除被标记为 exclusion 的科室。

## 6. 推理示例

### 例1：单症状
```
输入: "我头晕"
症状: [头晕 (1.0)]
命中: IF 头晕 THEN 神经内科 (1.2)
     IF 头晕伴低血压 THEN 心血管内科 (0.9)
结果: 神经内科 (100%) | 备选: 心血管内科
```

### 例2：组合症状（触发组合规则）
```
输入: "发烧咳嗽"
症状: [发热 (1.08), 咳嗽 (1.0)]
命中: IF 咳嗽 THEN 呼吸内科 (1.4)  ← 单症状
     IF 发热 THEN 普通内科 (1.08)   ← 单症状
     IF 发热+咳嗽 THEN 呼吸内科 (1.6×1.2) ← 组合规则加权
结果: 呼吸内科 (100%) [CRITICAL] | 备选: 普通内科
```

### 例3：紧急场景
```
输入: "胸闷心悸"
症状: [胸闷 (1.3), 心悸 (1.2)]
命中: IF 胸闷 THEN 心血管内科 (1.5)     ← high级别
     IF 心悸 THEN 心血管内科 (1.4)       ← high级别
     IF 胸闷+心悸 THEN 心血管内科 (1.7)   ← critical组合规则
结果: 心血管内科 (100%) [CRITICAL]
     ↑ 严重度升级：两个高位症状+危急组合规则
```

## 7. 规则管理

### 7.1 API 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/rules` | 获取所有规则（`?type=single\|compound\|exclusion`） |
| POST | `/api/rules` | 新增规则 |
| PUT | `/api/rules?rule_id=N` | 更新规则 |
| DELETE | `/api/rules?rule_id=N` | 删除规则 |
| GET | `/api/symptoms` | 获取症状列表 |
| GET | `/api/departments` | 获取科室列表 |

### 7.2 Web 管理界面

Web 端提供可视化规则管理：
- 规则列表表格（按类型筛选）
- 新增/编辑规则弹窗
- 一键删除确认
- 实时规则数量统计

## 8. 扩展性

规则库设计支持持续扩展：
- 新增症状只需在 `symptoms` 表添加一行
- 新增科室只需在 `departments` 表添加一行
- 新规则通过 Web 界面或 API 即时添加，无需重启服务
- 组合规则的 `extra_symptom_ids` 支持任意数量症状 AND 逻辑
